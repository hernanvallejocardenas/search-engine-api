# Search Engine API

A web API for the text search engine. It serves the same inverted-index
search over five Project Gutenberg books, with the index stored in a
SQLite database instead of a JSON file.

## How it works

An inverted index maps each word to the documents that contain it, along
with the position of each occurrence. Searching a word means looking it up
in the index instead of scanning every document. A multi-word query
returns only documents containing every word (AND). Results rank by total
term frequency divided by the square root of the document length, so
documents that mention the query often rank higher while shorter documents
still get a fair chance. A query in double quotes is a phrase search: only
documents containing the exact phrase, in order, match.

Tokenization lowercases text and splits on anything that is not a letter
or a digit, so search is case-insensitive and punctuation-tolerant.

## How the index is stored

`build_db.py` reads the corpus and writes `search.db`, a SQLite database
with two tables:

- `documents(id, filename, title, text, length)` — one row per book.
  `length` is the document's token count, used for ranking.
- `postings(term, doc_id, positions)` — one row per (term, document).
  `positions` is a JSON array of token offsets where the term occurs.

`search.db` is a build artifact. It is regenerated by `build_db.py` and
is not committed to the repository. The API opens it read-only.

## Endpoints

### GET /health

```
$ curl localhost:8000/health
{"status":"ok"}
```

### GET /search?q=<query>

Ranked results. Each result has the document file name, title, relevance
score, and a short snippet showing the query in context. An empty query
returns an empty result list.

```
$ curl "localhost:8000/search?q=alice"
{"query":"alice","results":[{"filename":"alices-adventures-in-wonderland.txt","title":"Alice's Adventures in Wonderland","score":2.3042,"snippet":"The Project Gutenberg eBook of Alice's Adventures in Wonderland This eB..."}]}

$ curl "localhost:8000/search?q=sleepy%20hollow"
{"query":"sleepy hollow","results":[{"filename":"the-legend-of-sleepy-hollow.txt","title":"The Legend of Sleepy Hollow","score":0.3771,"snippet":"..."},{"filename":"alices-adventures-in-wonderland.txt","title":"Alice's Adventures in Wonderland","score":0.0343,"snippet":"..."}]}

$ curl "localhost:8000/search?q=%22once%20upon%20a%20midnight%20dreary%22"
{"query":"\"once upon a midnight dreary\"","results":[{"filename":"the-raven.txt","title":"The Raven","score":0.0153,"snippet":"...VEN *** The Raven by Edgar Allan Poe Once upon a midnight dreary, while I pondered..."}]}

$ curl "localhost:8000/search?q=quantum"
{"query":"quantum","results":[]}
```

### GET /documents

Every indexed document, with file name and title.

```
$ curl localhost:8000/documents
[{"filename":"alices-adventures-in-wonderland.txt","title":"Alice's Adventures in Wonderland"},{"filename":"the-gift-of-the-magi.txt","title":"The Gift of the Magi"},{"filename":"the-legend-of-sleepy-hollow.txt","title":"The Legend of Sleepy Hollow"},{"filename":"the-raven.txt","title":"The Raven"},{"filename":"the-yellow-wallpaper.txt","title":"The Yellow Wallpaper"}]
```

## Setup

Requires Python 3.12.

```
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Build the database

```
python build_db.py
```

Reads the five `.txt` files in `corpus/` and writes `search.db`
(5 documents, 5,957 unique terms). Re-running the script rebuilds the
database from scratch. The database path can be changed with
`--corpus` and `--db`; the API reads the `SEARCH_DB` environment
variable when set, defaulting to `search.db` next to `main.py`.

## Run the server

```
uvicorn main:app --reload
```

The API listens on `http://localhost:8000`. Interactive docs are at
`http://localhost:8000/docs`.

## Run the tests

```
pytest
```

8 tests, all passing. Coverage: health, single-term search, multi-term
AND search, phrase search, missing term, empty query, case-insensitivity,
and the documents list. The test fixture builds a fresh SQLite index from
the real corpus into a temporary directory, so the tests exercise the
full stack (SQLite index to HTTP endpoints) with real data.

## Deploy on Render

Prerequisites: a Render account and a GitHub repository containing this
project.

1. Push the repository to GitHub.
2. In the Render dashboard, choose New + > Blueprint and select the
   repository. Render reads `render.yaml` and creates the web service.
3. Render runs the build command (`pip install -r requirements.txt &&
   python build_db.py`) and starts the server with uvicorn on the port
   Render assigns (`$PORT`).
4. The service is live at the URL Render assigns
   (`https://search-engine-api.onrender.com` by default). The free plan
   spins down after inactivity; the first request after that takes
   around a minute to wake the service.

The same project can be deployed with Docker instead: `docker build -t
search-engine-api .` then `docker run -p 8000:8000 search-engine-api`.
The Dockerfile builds the database into the image, so no setup step is
needed at run time.

## Notes

- Stack: FastAPI + SQLite (standard library `sqlite3`). Python 3.12.
- Search semantics match the command-line search engine exactly
  (same tokenization, same AND and phrase rules, same ranking), so a
  query returns the same results from the API and from the CLI.
- The API opens the database read-only; indexing is a separate step
  (`build_db.py`), never a request-time operation.
